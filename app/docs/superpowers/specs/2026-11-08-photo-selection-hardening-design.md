# 选片系统收口与验收闭环设计

## 1. 背景与目标

本设计用于收口《修复与改进方案-v1.md》阶段 7 尚未完成的硬性要求，并补齐第 9 节验收所需的后台界面、数据隔离测试和真实隔离启动验证。

目标：

- 保证后台业务写入、`audit_log`、`change_event` 在同一个 SQLite 事务中完成；
- 消除跨影楼模板、账号迁移、媒体和下载 scope 的越权/绕过路径；
- 统一可见性与下载授权规则；
- 在不读取原始照片目录的情况下，用隔离 fixture 覆盖关键验收场景；
- 使用 `vue-router` 补齐后台客户、订单详情及客户端评论/下载入口；
- 仅在测试、构建和隔离服务验收均通过后，将方案第 10 节阶段 7 标记为完成。

不在本次范围内：

- 不修改生产 `data/app.sqlite`；
- 不修改 `爸妈摄影/` 下的原始照片；
- 不重新设计现有配色和视觉风格；
- 不引入除 `vue-router` 之外的新运行时依赖；
- 不部署到远程生产服务器。

## 2. 设计原则

1. **最小改动**：保留现有 Express、SQLite、Vue 和样式结构，不做无关重构。
2. **失败快速暴露**：无效 studio、模板、账号、下载 scope 或角色值直接返回明确错误。
3. **审计不可脱离业务成功**：关键业务写入失败时，审计和事件一并回滚；审计写入失败时，业务也不得提交。
4. **权限后端为准**：前端隐藏菜单只改善体验，所有 studio、角色、订单和照片边界由接口强制校验。
5. **测试先行**：每个安全或行为修复先增加能够证明当前缺陷的失败测试，再写最小实现。
6. **敏感信息最小暴露**：密码仅在创建/重置成功响应中一次性返回，不写入审计 payload、日志或测试输出。

## 3. 后端架构与数据流

### 3.1 统一 mutation 辅助函数

在 `src/http/createApp.js` 或独立的服务模块中提供统一写入入口，接口形态如下：

```js
withMutation({
  jobId: number | null,
  actor: req.actor,
  action: string,
  eventKind: string | null,
  payload: object,
}, (tx) => {
  // 只在 tx 内执行业务写入
  return result;
})
```

实现要求：

- 使用 `db.transaction()` 建立事务；
- 业务写入、`audit_log`、可选的 `change_event` 均在事务回调中执行；
- 对 payload 做字段白名单或敏感字段剔除；
- `jobId` 必须由已校验的订单归属得到，不能只信任 URL 参数；
- 失败时返回现有错误码并整体回滚；
- 账号级动作允许 `job_id = NULL`，但仍写入审计；
- 异步导入只保证“创建导入任务 + 初始审计/事件”原子，进度更新单独记录安全状态。

移除 `res.on('finish')` 作为关键审计机制。若保留 middleware，只能作为不重复写业务审计的兜底或诊断，不得静默吞掉关键审计失败。

### 3.2 需要接入 mutation 的写操作

至少覆盖：

- 客户创建、编辑、重置、启用/停用；
- 员工创建、编辑、重置、启用/停用；
- 套餐模板创建、编辑、删除；
- 订单创建、设置修改、发布、锁定、退回、提醒、结算；
- 选片人添加、编辑、删除；
- 照片隐藏/恢复；
- 导入任务创建；
- 后台评论已读和回复；
- 下载设置修改。

客户端选择、公开设置、提交、撤回、评论等已有业务事件也应保持和事务边界一致，不能在业务成功后再补一个可能失败的事件写入。

### 3.3 跨 studio 与输入校验

- 新订单复制模板前，查询 `package_template` 时同时验证 `template_id` 和当前 staff 的 `studio_id`；不匹配返回 404。
- 客户、员工、订单、选片人、照片、评论和下载包查询均继续使用 studio/job 归属条件。
- 员工 `role` 仅允许现有角色白名单（`admin`、`editor`）；`status` 仅允许 `active`、`disabled`。
- 重置或停用客户/员工时，在事务内递增密码版本并删除其现有 session。
- 防止管理员将自己停用或降权；若产品规则允许，需要保留至少一个可用 admin。
- 客户管理权限按当前方案收口为后台 staff 可用，员工账号管理仍仅 admin 可用；若现有测试与文档冲突，以方案原文为准并更新测试说明。

### 3.4 迁移回填

保留现有编号 SQL migration 机制，不重建数据库、不删除选择数据。将客户回填从 `connection.js` 的隐式逻辑迁移到版本化数据迁移步骤（若当前迁移架构不支持 JS 数据迁移，则新增明确版本化脚本并由 runner 调用）。

回填必须以 `(studio_id, phone)` 作为关联边界；重复执行幂等；旧选片人仍关联到正确客户。初始密码按既有环境变量策略生成并强制改密，随机密码不得写入日志。

## 4. 下载与媒体授权

### 4.1 单一下载授权规则

抽取统一的原片下载判断，供以下接口复用：

- 单张原片；
- 异步 packages；
- 兼容旧 `/originals.zip` 接口，或将其改为调用异步包逻辑。

规则：

- 选片中只能下载水印预览，且必须启用预览下载；
- 锁定前禁止原片下载；
- `original_download_scope = none` 时所有原片接口返回 403；
- `selected` 只允许最终可见选片；
- `all` 允许订单范围内全部非隐藏原片；
- 失效包返回 410/现有约定错误码并清理文件；
- 下载文件路径继续使用 realpath confinement。

### 4.2 媒体访问

- 原片直链查询必须包含 `hidden = 0`；
- 未登录返回 401；
- 跨订单和非本客户参与订单返回 404；
- 客户端、staff、预览、原片和 ZIP 复用相同的 job/photo 归属判断；
- 后台仍可查看隐藏照片，但客户不能通过任何路径访问。

## 5. 前端路由与页面

新增 `vue-router`，保留现有 `styles.css` 和可复用 API 封装。路由守卫只负责登录态和页面跳转，权限仍由后端接口决定。

### 5.1 后台路由

- `/admin/jobs`：订单列表、搜索、状态、未读评论数、进入详情；
- `/admin/customers`：客户搜索、创建、启用/停用、重置密码；成功后显示一次性登录信息卡片和复制按钮；
- `/admin/jobs/new`：基本信息、截止时间、模板选择/调整、下载设置、来源目录、导入进度、选片人、保存草稿/发布；
- `/admin/jobs/:id`：六个标签：概览、照片、选片人、评论、设置、日志；
- `/admin/staff`：保留现有 admin-only 入口，普通 staff 不显示；
- `/admin`：按角色重定向到订单列表或首次改密页面。

### 5.2 客户端页面

- `/login`、`/change-password`、`/me`、`/jobs/:id`、`/jobs/:id/selected`；
- 我的选片继续提供 mine/final/products 三个标签；
- 预览下载按钮根据接口返回的 `allow_preview_download` 隐藏或显示；
- 评论面板支持列表、发表、回复、编辑时限、软删除和未读标记；
- 微信内显示“请在浏览器打开”提示；
- 客户只能看到参与订单和后端返回的可见评论/事件。

### 5.3 错误处理

- 页面操作显示接口返回的中文错误信息和错误码对应提示；
- 过期/失败下载包显示状态和重新生成入口；
- 创建/重置密码卡片只在当前页面展示，不写入 localStorage；
- 路由刷新后通过 `/api/auth/me` 恢复会话，不依赖旧的手写 pathname 分支。

## 6. 测试设计

### 6.1 隔离 fixture

新增 `test/fixtures/`，使用脚本或测试 setup 生成 3 张小图片及其临时源目录。测试不得读取生产照片目录，也不得写入生产数据库。

### 6.2 后端回归覆盖

新增或扩展测试覆盖：

- admin 每类 mutation 的审计和事件同事务写入；失败时业务、审计、事件均回滚；
- audit payload 不含密码、token、哈希；
- 跨 studio 模板不能复制；
- 角色/状态非法值拒绝，自身 admin 保护；
- 重置/停用后旧 session 失效；
- 隐藏照片原片和预览均不可由客户访问；
- 新旧下载入口遵守 `none/selected/all`；
- 迁移旧数据保留选择，并按 studio 正确回填客户；
- 可见性服务覆盖评论、事件、他人选择和数量；
- 锁定后选择写接口 409，评论仍可发。

### 6.3 验收顺序

1. `npm test -- --run`；
2. `npm run build`；
3. `node --check` 关键 JS 文件；
4. 使用临时 `DATA_DIR`、临时端口（避免本机 3000 Docker 冲突）启动服务；
5. 逐项执行第 9 节中可由隔离数据验证的账号、订单、评论、下载、安全流程；
6. 对必须使用真实生产数据的照片完整性，仅做只读 fingerprint 对比，不改生产数据；
7. 只有证据完整时更新第 10 节阶段 7。

## 7. 完成标准

- 全部自动化测试通过，且新增测试真实覆盖本次缺口；
- 生产构建通过；
- 隔离服务 `/api/health`、登录、首次改密、媒体鉴权、导入、下载和后台主要页面可访问；
- `app/:memory:` 不再生成；
- 生产照片目录和生产数据库未被写入；
- 第 10 节如仍有无法真实验证的条目，必须保持未勾选并逐条说明，不得宣称全部通过。
